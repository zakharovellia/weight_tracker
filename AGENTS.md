## Проект

Личный трекер веса, питания и тренировок: FastAPI + vanilla JS + Chart.js (всё локально, без CDN). Репозиторий `zakharovellia/weight_tracker`.

- БД: PostgreSQL `postgres.storage:5432`, схема `weight` (`daily_weight`, `daily_nutrition`, `workouts`).
- Локальный запуск: `uv venv .venv && source .venv/bin/activate && uv pip install -r requirements.txt`, затем `uvicorn app.main:app --host 0.0.0.0 --port 8000` (пароль БД — из окружения, не коммитить).
- Деплой: push в `main` → GitHub Actions собирает образ `registry.askahomelab.ru/weight_tracker:<дата-ша>` → bump тега в devops (`k3s/weight-tracker.yml`) → ArgoCD. Адрес: `https://wt.aska.internal`.
- Кластер не мутировать вручную — всё изменения через git (GitOps; см. `devops/AGENTS.md`).

## karpathy-guidelines — правила кода

Источник: скилл `multica-ai/andrej-karpathy-skills` (наблюдения Андрея Карпаты о типовых ошибках LLM-кодинга). Приоритет — аккуратность выше скорости; для тривиальных задач — по ситуации.

1. **Думай, прежде чем кодить — не додумывай.** Фиксируй допущения явно; неясно — остановись и спроси. Есть несколько трактовок — покажи их, не выбирай молча. Есть решение проще — скажи.
2. **Простота прежде всего.** Минимум кода для задачи, ничего спекулятивного: никаких фич «на будущее», абстракций для одноразового кода, невыпрошенных «гибкости» и конфигурируемости, обработки невозможных сценариев. Написано 200 строк, а хватит 50 — перепиши. Проверка: «сеньор не назвал бы это переусложнением?»
3. **Хирургические правки.** Меняй только то, что требует задача: не «улучшай» соседний код, комментарии и форматирование, не рефактори то, что не сломано; стиль — как в репозитории, даже если ты сделал бы иначе. Заметил посторонний мёртвый код — упомяни, не удаляй; удаляй только осиротевшее из-за твоих правок. Проверка: каждая изменённая строка трассируется к запросу.
4. **Цель — проверяемый результат.** Превращай задачу в проверяемую цель («добавь валидацию» → «тесты на невалидный ввод, затем зелёные»; «почини баг» → «тест, воспроизводящий баг, затем зелёный»). Для многошаговых задач — короткий план «шаг → как проверю». Отчёт без результата проверки не принимается.
